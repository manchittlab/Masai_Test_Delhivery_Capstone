# Delhivery Last-Mile Delay Intelligence Pipeline

This is an offline analysis of **synthetic** shipments. It estimates delivery hours, predicts whether a parcel will miss its service promise, and combines delay alerts with three hub operating segments. No real Delhivery data was used.

## How to run

From a fresh clone with Python and `pip` available, run these commands in order from the repository root:

```bash
pip install -r requirements.txt
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

The generator prints `24 1224 48`. All inputs and output files are in this repository; no network service or API key is required. `python package_model.py` regenerates `models/delay_model.pkl`. The committed pickle loads reliably only with the scikit-learn version pinned in `requirements.txt`; if the grader has a different installed version, it should run `package_model.py` instead of loading the committed pickle. Results in `outputs/` are regenerated by the scripts. The shared cleaning and feature functions in `src/shipment_prep.py` are used for both training data and new parcels. Do not change the order of the 17 pinned features.

## Data findings

- Deduplication removes 24 of 1,224 raw rows. The modelling table contains 1,200 unique shipments, of which 278 (23.17%) missed their promise (`outputs/part_a_checks.csv`).
- Express has the highest delay rate: 119 of 243, or 48.97%. Standard is 20.56% and Economy 8.57% (`outputs/part_a_delay_by_group.csv`). The service promises are different, so these figures are proportions late relative to each service's own promise.
- Delay rates rise from 4.00% in Tier 1 to 21.50% in Tier 2 and 44.00% in Tier 3 (`outputs/part_a_delay_by_group.csv`).
- The distance-band delay rates climb from 2.19% at 0–200 km to 13.68% at 201–400 km, 43.64% at 401–600 km, and 85.23% beyond 600 km (`outputs/part_a_delay_by_group.csv`).
- The three strongest absolute numeric correlations with delivery hours, excluding delivery hours itself, are `promised_hours` (+0.8372), `distance_km` (+0.4013), and `n_stops` (+0.3247) (`outputs/part_a_correlations.csv`). Correlation does not establish causation.
- Declared value is right-skewed: its filled-column mean is INR 1,533.0542 and median INR 1,121.50. After taking the natural log, mean 7.0277 and median 7.0224 are much closer, reducing the effect of very high values (`outputs/part_a_checks.csv`).

## Model results (regression)

- The mean-only baseline has validation R² of −0.0212: predicting one average for every parcel performs slightly worse than using the validation set's own mean (`outputs/part_b_metrics.csv`).
- Linear regression has the lowest validation RMSE, 4.8912 hours, and is the chosen model. Its one-time test RMSE is 4.5235 hours and test R² is 0.9493 (`outputs/part_b_metrics.csv`).
- A depth-1 tree has high bias: training RMSE 11.6334 and validation RMSE 12.1324. Depth 6 gives the best tree validation RMSE, 6.2796. An unlimited tree has training RMSE 0.0000 but validation RMSE 7.8368, a high-variance pattern (`outputs/part_b_tree_depth.csv`).
- Gradient boosting with learning rate 0.1 wins the rate experiment (validation R² 0.9306). At 0.01 it learns too slowly over 100 estimators (R² 0.7127); at 1.0 it overshoots useful updates (R² 0.8440) (`outputs/part_b_gb_learning_rate.csv`).
- Five-fold mean R² favors gradient boosting, 0.9353 versus linear regression's 0.9261 (`outputs/part_b_cv.csv`), while the held-out validation RMSE slightly favors linear regression (4.8912 versus 4.9165 hours). The prescribed choice is linear regression by validation RMSE. The 0.0253-hour difference is small; I would monitor both on later data before treating the ranking as stable.

## Model results (classification)

- Always predicting on time gives 76.67% validation accuracy but zero recall and zero F1: all 42 delayed validation parcels are missed (`outputs/part_c_models.csv`).
- The five bookkeeping/noise columns together account for 22.45% of the full forest's impurity importance, but all five rank outside the top seven by training-only univariate F-score. This shows why impurity importance alone is not evidence that a bookkeeping field is useful (`outputs/part_c_feature_scores.csv`).
- Seven selected features give the best measured validation F1, 0.8333, among the tested values of k. The k=5 result is 0.6988, and k=17 is 0.7848 (`outputs/part_c_selectk.csv`). Feature selection is fitted only on training rows.
- The untuned 7-feature forest wins validation F1 at 0.8333; grid search gets 0.7750 and randomized search 0.7848 (`outputs/part_c_tuning.csv`). Tuning did not help on this 180-row validation set. Small differences can be unstable, so the search result is not proof that the default settings will always be better.
- The operations rule chooses threshold **0.5**, the highest threshold with validation recall at least 0.80. At 0.5, validation precision is 0.7955 and recall is 0.8333; at 0.6, precision improves to 0.8889 but recall falls to 0.7619 (`outputs/part_c_thresholds.csv`).
- The one-time test gives precision 0.6889, recall 0.7561, and F1 0.7209 (`outputs/part_c_final_test.csv`). Test recall is lower than validation recall 0.8333. Only 41 test parcels are delayed, so each additional miss shifts recall noticeably.

## Operations recommendation

- Apply the **Escalate** playbook to HUB13 Nagpur, HUB15 Kochi, HUB17 Patna, HUB18 Ranchi, HUB19 Guwahati, HUB20 Raipur, HUB21 Bhubaneswar, HUB23 Siliguri, and HUB24 Agartala. Their respective delay rates are 0.4600, 0.3600, 0.4600, 0.3800, 0.6200, 0.4800, 0.4000, 0.4400 and 0.5400 in `outputs/hub_profile.csv`; the nine-hub segment mean is 0.4600 (`outputs/segment_profile.csv`).
- Four labels disagree with measured operation: HUB07 Kolkata is Tier 1 but **Watch**; HUB13 Nagpur and HUB15 Kochi are Tier 2 but **Escalate**; HUB22 Dehradun is Tier 3 but **Watch** (`outputs/tier_vs_segment_mismatch.csv`). Use these observed segments for the playbook instead of assuming the tier label describes current behavior. Review these hubs with local managers before changing a formal tier designation.
- Alert at probability **0.5** (`outputs/part_c_final_config.csv`). On the test set, about **6.9 of every 10 flagged** parcels are delayed (precision 0.6889), and about **7.6 of every 10 delayed** parcels are caught (recall 0.7561). Those rates are estimates from a small synthetic test set, not guarantees (`outputs/part_c_final_test.csv`).
- Among 48 new shipments, **8** are flagged: **6** require a hub-manager escalation and **2** get a proactive customer call (`outputs/new_shipment_actions.csv`).
- Keep K=3, the number of supported operations playbooks: its across/within distance ratio is 5.3928 with segment sizes 9-8-7. K=4 and K=5 have larger ratios, 6.3047 and 6.8866, but include groups of only 4 and 2 hubs respectively, too small to justify a separate playbook (`outputs/part_d_separation.csv`).

## Production plan

| Readiness characteristic | Concrete repository item |
| --- | --- |
| Accuracy | Regression and classification validation and one-time test metrics in `outputs/part_b_metrics.csv` and `outputs/part_c_final_test.csv`. |
| Reliability | Reload comparison in `outputs/part_d_reload_check.csv` measures a 0.0 probability difference on 180 test parcels. |
| Reproducibility | Pinned `requirements.txt`, committed generator/data, fixed split seeds and ordered commands above. |
| Performance | Seven selected classification features; batch scoring of 48 parcels with one loaded model. Measure runtime before setting a production latency target. |
| Maintainability | Shared constants, cleaning and feature construction in `src/shipment_prep.py`. |
| Consistency | `predict_delay.py` reuses those functions and stored historical medians and feature order. |
| Monitorability | Shipment actions, threshold and model checks are saved as CSV files for auditing. |

Monitor outcomes after delivery, with alerts that trigger investigation rather than automatic policy changes:

- Weekly delayed share: investigate if it differs by more than **5 percentage points** from the 0.2317 historical share for two consecutive comparable weeks.
- Weekly share flagged: investigate if it is above **30%** or below **5%** of dispatched parcels; investigate sale weeks separately.
- Recall on parcels whose actual delivery outcome is known: investigate if it falls below **0.65** in a rolling four-week window with at least **40 delayed parcels**.
- Check missing feature rates as well; investigate if any input has more than **5%** missing values in a week.

Retrain monthly after outcomes arrive, and sooner if these monitoring triggers persist. Evaluate sale-window parcels (`sale_event_flag=1`, 15–28 September) against comparable sale periods, not ordinary weeks. Drift here could mean changes in distance, hub load, rain, service mix, flag rates, or the relationship of those features to actual delays. Compare predictions and outcomes by hub and service type before releasing a replacement model.

## Limitations

- Every shipment is synthetic. Accuracy, hub differences and recommended actions may not carry over to Delhivery's real network.
- The test set has only 41 delayed parcels, making recall and precision estimates uncertain.
- The final classifier, its seven features and the threshold were chosen using one 180-row validation set. The result needs later time-based validation on unseen operational periods.
- The generated data uses a 90-day period and a single sale event; it cannot establish long-term seasonal behavior.
- The generated hub effects and noisy bookkeeping columns are controlled by the simulation. Real data may have different drivers, missingness, and operational costs. The alert policy should be calibrated against actual cost of missed delays versus unnecessary contacts.
